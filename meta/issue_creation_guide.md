# issue 作成ガイド

このリポジトリの実行時間改善・使い勝手改善・新ライブラリ作成について、候補の調査から GitHub issue の作成までを進めるための基準を定める。利用者が競技中に得られる効果を重視し、調査の詳しさや issue の件数を成果の代わりにしない。

その都度の依頼に対象・件数・成果物の指定があれば、その指定を優先する。実装・ドキュメント・検証の共通ルールは [AGENTS.md](../AGENTS.md)、コマンドの詳細は [scripts/INFO.md](../scripts/INFO.md) に従う。

このガイドを初版として運用し、判断のずれが見つかったら、対応する基準や例を逐次修正する。

## 基本方針

- 分野や分類ごとの件数は固定せず、有用性の高い候補を優先する。件数指定がなければ広く調べ、基準を満たすものを作成する。候補が少なければ少なくてよく、件数合わせの提案はしない。
- 主対象はライブラリの性能・API・機能であり、docs 単独の改善も含める。開発スクリプト・CI・dashboard・テスト整備だけの改善は、通常の探索対象に含めない。採用案に必要な docs・verify の変更は同じ issue の範囲に含める。
- 使用頻度が低い高度なアルゴリズムも、典型用途と追加する価値を説明できれば対象にする。Library Checker の未対応問題を埋めること自体は目的にしない。
- 調査中に正しさのバグを見つけた場合は、再現・確認して `bug` の issue として別に作成する。
- 後方互換性の維持は不要。改善に必要なら API・型を変更し、関連コード・verify・docs をまとめて更新する。古い issue の互換性維持条件を、そのまま新しい提案の制約にしない。
- 1 issue は、採否と完了を独立に判断できる改善単位にする。関連するだけの案を詰め込まず、1つの変更に必要な作業を細切れにも分けない。
- 実測・試作・公式 judge の確認結果と、コードからの推測・設計案・今後の確認事項を区別する。未実行の計測値や AC を書かない。

## 調査の進め方

1. `git status --short` と差分を確認し、調査時の HEAD と対象コードを把握する。既存の未コミット変更を保持する。
2. 現在の code・docs・test を照合し、何ができて何が不足しているかを確認する。対象指定がなければ、ライブラリの各分野を見渡して候補を探す。
3. open / closed issue、コメント、関連コミットを確認する。同名の機能だけでなく、別名の実装や既存 API の組合せも探す。closed だから実装済みとは限らないため、完了・不採用・取り消しの理由を読む。
4. 各候補について、利用場面、現状の負担、改善の仕組み、既存機能との差、確認方法を整理する。計算量やアルゴリズムの成立条件が不確かなら、一次資料や小規模な検証で根拠を確かめる。
5. 同じ原因・目的の候補を整理し、分類ごとの基準で採否を判断する。過去に不採用となった案を再提案するなら、その理由を解消する新しい根拠を示す。
6. 作成直前に対象コードと既存 issue を再確認し、重複や調査後の実装を除く。採用候補を GitHub に作成し、最後に一覧を報告する。

`TODO.md`、`implement_idea.md`、`meta/library_checker_gap_report.md` は探索の手掛かりとして使う。古い記載を現在の未実装・未解決の証拠にせず、現行コードと照合する。外部の問題や資料を根拠にする場合も、本文・制約・要求する操作を確認する。

issue 作成のために本体実装を完成させる必要はない。必要な試作や局所計測は一時ディレクトリなどで行い、調査の依頼だけで本体や生成 dashboard の変更を混ぜない。公式 judge や全件 verify も一律には実行しない。

## 実行時間改善

### 候補にする根拠

現行コードのどの処理を、なぜ減らせるかを示す。不要な走査・コピー・確保・前計算、重複する探索、計算量の改善などを、実際の呼び出し方や入力規模に結び付ける。「高速化できそう」だけでは候補にしない。

未計測でも、有望な仮説を調査用 issue にしてよい。その場合は未計測と明記し、効果を期待する理由、主要な大入力、悪化し得る条件、比較方法を示す。試作や計測を issue 作成の必須条件にしない。

### 実装を採用する基準

- 代表的な大入力で、測定誤差を除いて再現する悪化があれば原則不採用とする。平均や一部の大幅な改善で、主要ケースの悪化を相殺しない。
- ライブラリの主用途で効果を判断する。実際には使わない型や操作列だけで速くなることを、採用理由にしない。
- 小入力だけの改善でも、実際によく使う条件で効果があり、代表的な大入力を悪化させず、コード増加が小さければ候補にする。すべての入力規模で速くなることまでは要求しない。
- 大入力で明確な効果があり、複雑さの増加が小さい案を優先する。数％の改善のために分岐や専用実装を大きく増やす案は避ける。根拠のない一律の改善率は設けない。
- 速度を重視し、想定 judge のメモリ制限内なら、前計算やキャッシュによるメモリ増加を広く許容する。前処理・入力・一時領域も含めた使用量と増加を確認する。
- 明確に速くなるなら、明示的な `build`、キャッシュ管理、方式選択を伴う API も許容する。必要な手順と効果が出る条件を説明する。
- 利用する judge の GCC / x86-64 を基本にし、SIMD や環境専用の実装も候補に含める。必要な命令セット・コンパイラ条件・実行可否を明記し、手元の CPU の結果をすべての judge に当てはめない。

調査用 issue は、改善しないことが分かった場合も、不採用の根拠と計測結果を残して調査を完了できる形にする。完了のために変更を無理に採用したり、別の高速化が見つかるまで探索を続けたりする条件は付けない。

### 比較計測の考え方

比較対象は現在の実装とし、同じ入力・環境・コンパイル条件で測る。性能計測は現在のリポジトリ設定に合わせ、通常の verify と区別して assert を無効にする。既定は GCC・C++17・`-O2` で、`measure_verify.py` は `-ULOCAL -DNDEBUG` を追加する。並列 verify の wall time を性能値にしない。

測定ケースは変更の影響から選び、一律に全種類を並べない。

- 主用途の代表的な大入力と、制約上限付近の入力を含める。
- 分岐やデータ分布で差が出るなら、乱数・整列・同値、疎・密、短い・長い区間など、関係する条件を分ける。
- 小入力や閾値の前後も確認し、大入力での改善と取り違えない。
- 前計算・キャッシュは、構築込みの単発・少数・多数の問い合わせを比較する。都合よく構築費用を除かない。
- 部品単体の計測に加え、主要な呼び出し元を通した実行時間を確認する。省いた処理の回数だけから全体の速度向上を断定しない。
- 結果の一致を確認し、入力生成を含めるか、確保・構築・返却をどこまで含めるかをそろえる。

比較順序を交互にして複数回測り、中央値とばらつきを確認する。必要に応じて warmup や CPU 固定を使う。差が測定誤差と区別できなければ、改善・悪化を断定しない。

issue に実測を載せる場合は、代表ケースの変更前後の時間、入力条件、計測範囲、環境・コンパイル条件・反復方法を短く示す。改善しなかった主要ケースや未測定の条件も隠さない。大量のログや全ケース表を本文へ貼る必要はない。

## 使い勝手改善

利用側が現在何を記述・管理していて、変更後に何を省けるかを示す。必要なら短い使用例で違いを伝える。

- 繰り返し書く処理や間違いやすい手順を減らせるなら、小さな API 追加や薄いラッパーも対象にする。
- 復元、複数ライブラリの接続、結果の取得、型や引数の扱いなど、利用時の具体的な負担を減らす。単に別名を増やすだけの案は避ける。
- 新 API の追加だけでなく、既存 API の整理・置き換えも検討する。短く自然に使える interface を優先し、互換用の入口を増やさない。
- 値や頂点番号の意味、失敗時の返り値、状態変更や再利用の条件など、その変更で判断が必要な契約を示す。無関係な境界条件を網羅的に列挙しない。
- 性能を主張しない小さな API 改善に、一律の性能計測を要求しない。実行経路や計算量を変える場合は、その影響を確認する。

## 新ライブラリ作成

「何のアルゴリズムか」に加え、「どのような問題で何が必要になり、現行ライブラリでは何が足りないか」を説明する。使用頻度や実在の出題例だけで足切りせず、典型用途が説明できることを重視する。

初版は典型用途を無理なく扱う最小構成にする。関連機能をすべて入れず、独立した価値のある拡張は別 issue にする。既存部品の組合せで十分なら新実装を増やさず、その組合せを使いやすくする API が必要かを検討する。

主要な操作、入力・返り値、必要な制約、時間・空間計算量、既存部品を使う方針を、提案の判断に必要な範囲で示す。計算量の最悪・償却・期待を区別し、未確認の目標を確定した保証として書かない。

実装方針が固まっていなくても、用途・既存実装との差・成立しそうなアルゴリズム・検証方法を説明できれば、調査用 issue にしてよい。未確定の設計や計算量を明記し、実現性の確認も完了条件に含める。実現できないと分かった場合は、その根拠を残して調査を完了する。

直接対応する Library Checker・yukicoder・AOJ の問題がなくても対象にできる。その場合は、愚直解・全列挙・独立した oracle との比較など、`STANDALONE` による検証方針を必ず示す。judge 問題がある場合も、その問題では検査されない追加 API や重要な契約を確認する。新規実装には最も具体的な domain のライブラリ本体、対応する `_md`、少なくとも1本の verify を含める。

## docs 単独の改善とバグ

docs は、誤った仕様・計算量、使い方の理解を妨げる不足や表現を対象にする。何が誤解されるか、何を正しく伝えるかを示し、単なる好みの言い換えや表記統一だけでは issue にしない。実装の誤りを説明の書き換えで正当化しない。

バグは改善提案とは分け、再現条件、期待する結果、実際の結果、対象コードを示す。入力が公開された前提条件を満たすかを確認し、未確認の疑いを確認済みのバグとして登録しない。

## issue 本文の書き方

日本語で簡潔に書く。タイトルは対象と変える内容が分かるものにする。本文は現状・用途・提案・完了条件を中心とし、計測や細かな根拠は判断に必要なものだけ載せる。

- 対象コードや関連 issue にリンクし、調査の基準が分かるようにする。コードの挙動を根拠にするリンクは、可能なら調査時の commit に固定する。
- 提案と確定仕様を区別する。API 名や内部構造の細部まで、理由なく実装者の選択を固定しない。
- 実装者が判断するのに必要な前提や制限は残す。文量を増やすための一般論、全 issue 共通の長い注意書き、過剰な境界値の列挙は避ける。
- 共通の実装・docs・検証ルールは `AGENTS.md` を参照し、issue 固有の確認事項を中心に書く。

標準の構成は次のとおり。不要な見出しや項目は省き、空欄のまま投稿しない。

```markdown
## 現状・用途

対象コードと、利用時に困ること・足りないこと。
既存機能で代替できない理由や、関連 issue との差。

## 提案

変える内容と、効果が出る仕組み。
必要なら短い API 例、前提・計算量・メモリへの影響。
調査用なら、仮説と未確認の点。

## 確認したこと

実施したコード確認・試作・計測などのうち、採否に関わる根拠。
未計測ならその旨と、今後確認する条件。

## 完了条件

- この issue で実現・判断する結果。
- 重要な契約・検証対象。
- 高速化なら主要な大入力を含む比較と、悪化時の不採用判断。
```

分類ごとに、次の情報を優先する。

| 分類 | 本文に必要な中心情報 | label |
| --- | --- | --- |
| 実行時間改善 | 現行の負担、削減の仕組み、主用途・大入力の比較方針、採否の条件 | `speed up` |
| 使い勝手改善 | 利用側の負担、変更後の使い方、必要な API 契約 | `enhancement` |
| 新ライブラリ | 典型用途、既存実装との差、最小構成、検証方法 | `new library` |
| docs 単独 | 誤り・不足とその影響、正しく伝える内容 | `documentation` |
| バグ | 再現条件、期待結果・実際の結果、修正の確認方法 | `bug` |

label は既存の分類を使い、作成時に利用可能なものを確認する。調査用かどうかは本文で明示し、そのためだけに新しい label を増やす必要はない。

## 作成と報告

「issue を作って」と依頼された場合は、基準を満たす issue を GitHub に作成するところまで進める。候補一覧の承認や本文案の確認を、毎回の必須手順にはしない。依頼が候補出し・下書き作成・ガイドの編集に限られている場合は、その範囲の成果物を作る。

このガイドで判断できる事項は毎回聞き直さない。依頼との矛盾や、採否を変える未確定の用途・制約がある場合だけ、必要な質問をする。

作成後は、issue のリンク・分類・狙いを一覧で報告する。重要な見送り候補があれば、既存実装との重複、主用途で効果なし、大入力で悪化など、理由を短く添える。調査段階の未計測と、確認済みの結果を区別する。作成できなかったものを作成済みと報告しない。

## 過去の判断例

以下は判断の参考であり、本文の長さや当時の制約をそのまま模倣するための見本ではない。現在の方針と実装を優先する。

- [#253 RadixHeap](https://github.com/firiexp/library/issues/253): 重い payload の局所計測では速くなったが、主用途の Dijkstra で採用する効果を確認できず、実装を取り消した。主用途で評価する例。
- [#293 TwoSAT](https://github.com/firiexp/library/issues/293): 変数番号と bool 値で節を追加し、利用側の変換を減らす。小さな API 追加にも用途がある例。
- [#40 重心分解の距離区間和](https://github.com/firiexp/library/issues/40): 既存部品の接続と差し引きの管理を内部にまとめる。利用側の負担を減らす例。
- [#82 区間ソートと区間積](https://github.com/firiexp/library/issues/82): 既存構造にない操作を加え、初版の制約と償却計算量を示す。新ライブラリの範囲を定める例。
